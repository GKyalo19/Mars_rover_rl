### Industry parallel

In robotics autonomy stacks you usually separate:

| Layer | Meaning | In our project |
|-------|---------|----------------|
| **World / scenario** | Maps, obstacles, mission goals | This chapter |
| **Robot + controllers** | Embodiment + low-level actuators | Ch.3 / 3b / 4 action term |
| **Autonomy / policy** | Decides where to go | PPO in Ch.7 |
| **Evaluation scenarios** | Harder maps, held-out goals | Ch.9 |

Game studios call this **level design**. Autonomous-vehicle teams call it **scenario generation**. Same idea: the learner is only as good as the distribution of worlds it practiced on.

### Path planning connection (again, clearer)

We still are **not** shipping a classical planner (A\*, RRT\*) in Phase A.

Instead:

1. Every episode spawns a **goal** somewhere reachable-ish on the terrain.  
2. Obstacles make straight lines unsafe.  
3. Rewards punish crashes and reward progress.  
4. The policy learns a **reactive** strategy: given local sensing + goal direction, choose \([v,\omega]\).

That reactive strategy *behaves like* path planning when you watch a rollout — but the “planner” is the neural net, not a separate geometry algorithm. Chapter 8 can add explicit reach-avoid / planner layers later.

## 6.1 Jargon, explained properly

### Terrain

**Terrain** means the ground surface the rover drives on — hills, flats, craters, roughness — not including free-floating decorations in the sky.

In Isaac Lab, terrain is often represented as:

- a **height field** (a grid of elevation values), or  
- a **USD mesh** (an artist-made or scanned ground model).

Think of a height field as a spreadsheet of heights: each cell says “at this XY, the ground is this high.” PhysX then lets wheels collide with that surface.

### Procedural generation

**Procedural** means “generated by an algorithm from parameters,” not hand-sculpted in Blender every time.

Example parameters:

- number of rocks  
- rock height range  
- map size  
- roughness  

**Why industry loves this for RL:**  
You can create **thousands of slightly different maps** so the policy cannot memorize one layout. That improves **generalization** (doing well on new maps, not only the one you overfitted).

### Domain randomization (preview)

**Domain randomization** means randomly varying simulation details (friction, rock density, lighting, goal distances) during training so the policy becomes robust.

Terrain randomness is one big piece of domain randomization. You will expand this in later training configs; Chapter 6 gives you the knobs.

### Obstacle

An **obstacle** is anything the rover should not drive through: rocks, scarps, posts, etc.

Two implementation styles:

| Style | What it is | Pros | Cons |
|-------|------------|------|------|
| **Geometric primitives / height-field pillars** | Cubes/columns baked into the height map | Fast, easy, great for Phase A learning | Looks less like real Mars |
| **USD rock assets** | Nice meshes (RLRoverLab style) | Visual fidelity, realistic contacts | Heavier pipeline, more asset work |

**Our Phase A choice:** start with Isaac Lab **discrete-obstacle height-field terrain** (procedural).  
**Phase B / polish:** optionally swap in USD Mars ground + rock meshes inspired by RLRoverLab’s `terrain_only.usd` / `rocks_merged.usd` split.

### Goal / target / command

In everyday speech: “go over there.”

In Isaac Lab MDP language, that destination is often a **command** — a per-env target the environment keeps updating or holding for the episode.

You already referenced this in Ch.4–5 as:

```text
command_name = "target_pose"
```

A **command manager** stores, for each parallel env, something like:

- goal position relative to the robot, and/or  
- desired heading  

Observation terms read it (`distance_to_goal`). Reward terms read it (`progress_to_goal`). Reset logic samples a new one each episode.

### Reachable goal

A goal is **reachable** if a capable driver *could* get there without requiring magic (teleport through rocks, drive off the map, etc.).

If you sample goals inside rock volumes or beyond cliffs, you poison training: the agent is punished for failing an impossible exam.

RLRoverLab’s approach (idea to steal): sample goals using **terrain-aware** logic — e.g. on the mesh / flat patches — not blind uniform random XY in empty space.

For Phase A procedural terrain, we approximate “reachable” by:

- sampling on the flat-ish platform / away from map borders  
- keeping a minimum clearance from the densest obstacle region  
- rejecting goals too close or too far from the spawn

### Episode reset / event

An **event** in Isaac Lab is something that happens at a lifecycle moment:

- on startup  
- on **reset** (when an episode ends and a new one begins)  
- at intervals  

Resetting typically:

1. places the rover at a start pose  
2. samples a new goal command  
3. clears buffers (episode length, etc.)

### Scene configuration (`InteractiveSceneCfg`)

A **scene cfg** is the shopping list of everything that exists in one env clone:

- ground / terrain  
- obstacles  
- robot articulation  
- lights  
- sensors (contact, ray caster / height scanner)  

This is the USD/PhysX “level” definition in code form.

### Environment origin / env spacing

With **vectorized** training you run many envs at once. Each env has an **origin** in the world so clones do not overlap.

`env_spacing` is roughly “how far apart to place parallel Mars yards.”

### Curriculum (optional concept)

A **curriculum** gradually increases difficulty (fewer rocks → more rocks, closer goals → farther goals).

We mention it so you recognize the word; Phase A can use a fixed medium difficulty first. Curriculum is a later upgrade when training plateaus.

## 6.2 Two ways to build “Mars” (choose Phase A, know Phase B)

### Path A — Procedural height field (recommended now)

Use Isaac Lab’s built-in generators (e.g. discrete obstacles on a flat platform).

**You get:**

- no need for external Mars USD downloads to start learning the wiring  
- fast iteration on NVIDIA  
- enough structure for navigation + collision learning  

**You do not get yet:**

- photoreal Jezero-looking geology  

That is OK. Policies learn geometry and goal-seeking first; prettier ground can come after the MDP works.

### Path B — USD Mars kit (RLRoverLab-inspired later)

RLRoverLab’s Mars scene roughly splits assets like:

| Asset | Role |
|-------|------|
| `terrain_only.usd` | Driveable ground |
| `rocks_merged.usd` | Visible obstacles (contact) |
| `terrain_merged.usd` | Hidden merged mesh for ray casting |

Why split? Their comment is practical: ray casters often behave better with a **single merged** mesh for height scans, while you still want separate visible rocks for rendering/contacts.

**We will not require Path B to finish Chapter 6.** Know it exists so your architecture stays compatible.

## 6.4 Procedural Mars terrain — full code to copy

### File: `mars_rover/assets/terrains/mars/mars_terrain_cfg.py`

Read this as a **recipe for random rock yards**, not as mysterious config noise.

```python
# Copyright (c) 2026, Mars_rover_rl contributors.
# SPDX-License-Identifier: BSD-3-Clause

"""Procedural Mars-like terrain settings (Phase A).

This uses Isaac Lab height-field generation with discrete obstacles.
It is intentionally simple: a flat-ish platform with rock-like pillars.

Requires Isaac Lab (NVIDIA) to import and spawn.
"""

from __future__ import annotations

from isaaclab.terrains import TerrainGeneratorCfg, TerrainImporterCfg
from isaaclab.terrains.height_field import hf_terrains_cfg
from isaaclab.utils import configclass


@configclass
class MarsProceduralTerrainCfg(TerrainImporterCfg):
    """Terrain importer configured for Perseverance navigation practice.

    Key ideas:
      - terrain_type='generator' means 'build from algorithms,' not 'load one USD file.'
      - TerrainGeneratorCfg describes a grid of sub-terrains (even if 1x1 for starters).
      - Discrete obstacles approximate rocks without needing Blender rock packs yet.
    """

    prim_path: str = "/World/ground"
    terrain_type: str = "generator"
    terrain_generator: TerrainGeneratorCfg = TerrainGeneratorCfg(
        seed=42,  # set None later for more diversity; fixed seed helps debugging
        size=(40.0, 40.0),  # meters — large enough for short nav episodes
        border_width=3.0,
        num_rows=1,
        num_cols=1,
        horizontal_scale=0.1,  # grid resolution XY (smaller = finer, costlier)
        vertical_scale=0.05,  # quantization of heights
        slope_threshold=0.75,
        use_cache=False,
        sub_terrains={
            "rocks": hf_terrains_cfg.HfDiscreteObstaclesTerrainCfg(
                proportion=1.0,
                # Obstacle footprints (width) and heights in meters — tune to rover size.
                obstacle_width_range=(0.4, 1.2),
                obstacle_height_range=(0.3, 1.0),
                num_obstacles=60,
                platform_width=4.0,  # clearer spawn/goal area near center
                obstacle_height_mode="choice",
            )
        },
    )
    # Visual / debug
    debug_vis: bool = False
```

### What the important fields mean (plain English)

| Field | Meaning | Why you care |
|-------|---------|--------------|
| `size=(40, 40)` | Map is about 40 m × 40 m | Too small → trivial; too big → sparse learning early |
| `num_obstacles` | How many rock-like blocks | Difficulty dial |
| `obstacle_height_range` | How tall rocks are | Must be tall enough to matter vs rover |
| `platform_width` | Clearer central pad | Safer spawns/goals while learning |
| `seed` | Reproducibility | Same world while debugging rewards |
| `horizontal_scale` | Grid cell size | Finer mesh = prettier + slower |

**Tuning tip:** If the rover never finds a path, reduce `num_obstacles` first — do not immediately blame PPO.

### `{ENV_REGEX_NS}` — what is that weird string?

When Isaac Lab clones env 0, 1, 2, … it namespaces prims like `/World/envs/env_0/Robot`.

`{ENV_REGEX_NS}` is a **placeholder** meaning “insert the correct per-env namespace.”  
You almost always use it for robot and onboard sensors so clones do not fight over the same path.

## 6.6 Goal generator (commands) — full code to copy

### Why commands instead of hardcoding a pyramid “finish flag”?

Because every episode needs a **new** exam question. Commands are the MDP mechanism for “this env’s current target.”

### File: `envs/navigation/config/commands_cfg.py`

```python
# Copyright (c) 2026, Mars_rover_rl contributors.
# SPDX-License-Identifier: BSD-3-Clause

"""Goal commands for Perseverance navigation.

Phase A uses Isaac Lab's terrain-aware position command utilities when available.
If API names shift slightly in your Lab 3.x build, compare with:

  isaaclab.envs.mdp.commands

and with RLRoverLab's TerrainBasedPositionCommandCfg idea:
  sample a target pose related to the terrain, not blind empty space.
"""

from __future__ import annotations

import math

from isaaclab.envs.mdp import UniformPoseCommandCfg
from isaaclab.utils import configclass


@configclass
class CommandsCfg:
    """Command terms exposed to obs/reward code as command_name='target_pose'."""

    # NOTE:
    # UniformPoseCommandCfg is a solid Phase A starter: samples poses in ranges.
    # As you harden the stack, prefer a terrain-based sampler (RLRoverLab style)
    # so goals land on walkable surfaces.
    target_pose = UniformPoseCommandCfg(
        asset_name="robot",
        body_name="base_link",  # must match your articulation root / body name
        resampling_time_range=(150.0, 150.0),  # hold one goal for the episode window
        debug_vis=True,  # shows target marker in viewport — helpful while learning
        ranges=UniformPoseCommandCfg.Ranges(
            pos_x=(3.0, 12.0),   # meters ahead-ish relative sampling ranges
            pos_y=(-6.0, 6.0),
            pos_z=(0.0, 0.0),    # keep on ground plane logic / yaw focus
            roll=(0.0, 0.0),
            pitch=(0.0, 0.0),
            yaw=(-math.pi, math.pi),
        ),
    )
```

### How this connects to Chapters 4–5

| Earlier code | Needs from this chapter |
|--------------|-------------------------|
| `distance_to_goal(..., command_name="target_pose")` | A command literally named `target_pose` |
| `progress_to_goal` / `reached_goal` | Same |
| terminations `goal_reached` | Same |

If names disagree (`target` vs `target_pose`), nothing crashes at import — training just reads the wrong tensor or errors at runtime. **Names are contracts.**

### Making goals more “reachable” (practical rules)

While debugging, tighten ranges:

1. Start with closer goals: `pos_x=(2.0, 5.0)`.  
2. Increase distance as success rate rises (manual curriculum).  
3. If using procedural rocks, keep goals nearer the `platform_width` clear zone first.  
4. Later, replace uniform sampling with terrain-flat-patch sampling (advanced, RLRoverLab-like).

## 6.7 Reset events — full code to copy

### File: `envs/navigation/config/events_cfg.py`

```python
# Copyright (c) 2026, Mars_rover_rl contributors.
# SPDX-License-Identifier: BSD-3-Clause

"""Reset / randomization events for navigation episodes."""

from __future__ import annotations

from isaaclab.managers import EventTermCfg as EventTerm
from isaaclab.managers import SceneEntityCfg
from isaaclab.utils import configclass

import isaaclab.envs.mdp as mdp


@configclass
class EventCfg:
    """What happens when an episode starts or resets.

    Minimal Phase A:
      - reset robot root state (pose + velocity)
      - (commands resample according to their own resampling_time_range)

    Later upgrades:
      - randomize friction
      - randomize mass
      - randomize spawn yaw more aggressively
    """

    reset_base = EventTerm(
        func=mdp.reset_root_state_uniform,
        mode="reset",
        params={
            "pose_range": {
                "x": (-1.0, 1.0),
                "y": (-1.0, 1.0),
                "yaw": (-3.14, 3.14),
            },
            "velocity_range": {
                "x": (0.0, 0.0),
                "y": (0.0, 0.0),
                "z": (0.0, 0.0),
                "roll": (0.0, 0.0),
                "pitch": (0.0, 0.0),
                "yaw": (0.0, 0.0),
            },
            "asset_cfg": SceneEntityCfg("robot"),
        },
    )
```

### Reset vs command resampling — who does what?

- **Event reset** places the **rover**.  
- **Command term** defines / refreshes the **goal**.  

Both must cooperate: if you teleport the robot on top of a rock every reset, collision terminations fire immediately and learning dies.

## 6.9 End-to-end episode story (all chapters clicking)

1. **Reset:** rover placed near center platform; velocities zeroed.  
2. **Goal sampled:** `target_pose` appears some meters away.  
3. **Observe:** distance, heading, last action (Ch.4).  
4. **Act:** policy outputs \([v,\omega]\); differential drive spins wheels (Ch.4).  
5. **Physics:** wheels interact with ground + rock pillars.  
6. **Reward:** progress / success / collision / smooth / time (Ch.5).  
7. **Terminate?** success, crash, timeout, too far (Ch.5).  
8. If done → go to 1. Else → go to 3.  
9. After many steps across many envs → PPO update (Ch.7).

That loop *is* the product.
